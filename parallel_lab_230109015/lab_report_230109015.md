### Karp-Flatt diagnostic and forensic explanation

1. **Noise floor.** S₁ should be exactly 1, but it logs as 1.010 and 0.972. T₁ was measured separately from the p=1 row, so run-to-run noise is about ±3%. With IQRs of 3–9% of the median, differences smaller than about 10% between strides are not meaningful.
2. **e(p) rises under both strides.** It goes from about 0.12–0.15 at p=2 to about 0.33–0.38 at p=16–20. The two curves overlap within noise. The contrasts are stride 1 vs 16 at p=4 (0.194 vs 0.210), p=16 (0.333 vs 0.344) and p=8 (0.365 vs 0.291). The only points where stride 1 is clearly slower are p=8 (+19%) and p=20 (+15%). At p=4 and p=16 it is indistinguishable, and Table 1A points the other way.
3. **Interpretation.** A rising e(p) means the "serial" overhead grows with p. A fixed serial fraction would give a *constant* e(p). The false-sharing prediction was that e(p) climbs for stride 1 but stays flat for stride 16. That did not happen. Both curves climb, so the dominant overhead is **not coherence traffic**.
4. **Why the effect is buried (estimate).** At p=1 the loop costs about 4482 ms / 24M ≈ **187 ns per iteration**, which is interpreter-dominated. A cross-core invalidation costs on the order of 50–100 ns. If every store missed, the extra cost would be roughly +25–50% of the *compute* time. With 14 workers the ideal compute is about 24M/14 × 187 ns ≈ **320 ms**, so the false-sharing signal is about 80–160 ms. Meanwhile the measured T_p is 1100–1700 ms, which means roughly **0.8–1.4 s of overhead** per run. That overhead is **(hypothesis)** process creation on Windows. `spawn` starts workers one by one from the parent and re-imports the module in each. It is included in the timed region and grows with p, and it matches a rising e(p) independent of stride. The IQRs (43–143 ms) are as large as the signal. In compiled C the loop costs about 1 ns, so coherence would dominate. In Python the interpreter dilutes the effect.
5. **Test for the hypothesis:** time `p` workers with `iters=0` (start, attach, close, join). If that time is about 0.8–1.4 s at p=14, the overhead is confirmed. To expose false sharing, subtract it, or raise `M` by 10× so compute dominates.

### Amdahl ceiling

- Serial fraction s = T_StageA(1)/T₁ = **0.028469**, which means Stage A took about 100 ms of the 3526 ms at p=1.
- **S∞ = 1/s = 35.13**
- Theoretical speedup at p = 20: 1/(s + (1−s)/20) = **12.98**
- Observed S₂₀ = **3.82**, which is only **29%** of the Amdahl prediction.
- Karp-Flatt at p=20 from the strong data: e = (1/3.8198 − 1/20)/(1 − 1/20) = **0.223**. That is about **8×** the measured s = 0.028. The serial Stage A explains only about 1/8 of the lost scaling. The rest is parallel-stage inefficiency (see below). At p=7, e = 0.137, and at p=14, e = 0.233.

### SMT / hybrid-core inflection analysis

- **The real inflection is at p = 7 → 8, not at P_phys = 14.** Speedup climbs to a peak of 3.84 at p=7 and then *falls* to 3.20 at p=8. The marginal ΔS changes from +0.141 to −0.642. After that the curve is flat and noisy, between 3.2 and 3.85, for p = 8…20.
- **Lab-defined boundary (P_phys = 14 → 15):** average marginal speedup per worker is 0.1906 for p = 1…14 and 0.0570 for p = 14…20. That is a **70.1% drop** in marginal speedup per added worker. The single step 14 → 15 is actually +0.257, which is noise on a plateau.
- **Interpretation (hypothesis):** on a 6P + 8E hybrid part the OS would first fill the P-cores. Around p ≈ 7–8 it starts placing workers on SMT siblings and/or slower E-cores, so the added workers contribute almost nothing. The drop at p=8 itself is likely scheduler placement or a power/frequency step. The 4–5× efficiency collapse (E from 0.91 at p=2 to 0.19 at p=20) is larger than SMT and E-cores alone explain.

### 3A Measured ceilings (P_phys = 14)

| Quantity | Value |

| Compute (14 workers × 8×10⁷ FLOP in 6.814 s) | **P_sustained = 0.1644 GFLOP/s** |
| Ridge point I* = P/BW | **0.3052 FLOP/Byte** |

**These are not real hardware ceilings.**
- A 96 MB copy should take on the order of 10–30 ms on a modern laptop. Yours took 356 ms, which implies about 0.5 GB/s against a real DRAM bandwidth of tens of GB/s. The timed region almost certainly includes Windows shared-memory attach and first-touch page faults, and likely process start-up. Treat 0.54 GB/s as an *effective copy rate including overhead*. The true ridge point is probably much lower than 0.305.
- The compute ceiling works out to 0.1644 × 10⁹ / 14 ≈ **11.7 MFLOP/s per worker**. A single Python process typically runs several times faster on this loop. That is the same roughly **4× shortfall** seen in Phase 2, so the common cause is system-level and not specific to one kernel. This is the same **(hypothesis)** as before: power or thermal limits, E-core placement or Windows scheduling under all-core load.

| **3 Dynamic C = 256 (C\*)** | **5274.246** | 1.330 |
| 3 Dynamic C = 1024 | 10073.919 | 2.434 |

**C\* = 256** (lowest wall time among dynamic chunk sizes). Phase 4 hash inputs: T_wall(Strategy 1) = 6556.438 and T_wall(Strategy 3, C\*) = 5274.246.

### Analysis

1. **λ can be predicted from the work function.** Work per item is K(i) ≈ (i/60)², so cumulative work up to i is about i³/10800, and the total is 12000³/10800 ≈ 1.6×10⁸ iterations.
   - *Block static:* the last worker owns [11143, 12000), about **19.9%** of all work, against a fair share of 1/14 = 7.1%. The predicted λ ≈ 0.199 × 14 = **2.79**, and the measured value is **2.52** (the same order and close).
   - *Cyclic:* every worker gets items spread across the whole range, so λ ≈ 1.0. Measured 1.024.
   - *Dynamic C = 1024:* there are only ⌈12000/1024⌉ = 12 chunks for 14 workers, so 2 workers get nothing. The last chunk [11264, 12000) holds about **17.3%** of all work, so λ ≥ 0.173 × 14 = **2.42**. Measured **2.434**, which is an almost exact match.
2. **Trade-off between C = 1 and C = 1024:** C = 1 gives near-perfect balance (λ = 1.010), but 12,000 lock acquisitions on the shared counter make every worker wait. Wall time is 3× that of cyclic (13.1 s vs 4.3 s). At C = 1024 there are almost no lock operations, but chunks are so coarse that the last, heaviest chunk is a single worker's tail (λ = 2.43, 10.1 s). C = 256 gives 47 chunks, so about 3.4 chunks per worker, a small enough tail (λ = 1.33) and few enough lock operations. C = 64 is close (5826 ms, λ = 1.10), so the optimum is a broad minimum between 64 and 256.
3. **Caveats on the dynamic times.** Wall times for C = 1, 4 and 16 (11.4–13.1 s) do not scale with the number of claims (12,000 vs 3,000 vs 750), so a simple per-claim lock cost does not explain them. Run-to-run noise or system load likely contributes. Note also that t_worker includes time spent *waiting for the lock*, so λ near 1.0 does not mean the workers were computing efficiently. They were simply equally busy or equally blocked. Wall time is the more reliable column.
4. **Cyclic beat every dynamic setting** (4281 vs best 5274 ms). The skew here is smooth and monotonic, so round-robin spreads it almost perfectly with no synchronization at all. Dynamic scheduling pays off when the cost per item is *unpredictable* (graphs, sparse matrices), which this workload is not.

## 6. Summary of Findings and Exam Takeaways

- **Observed vs expected:** the Phase 1 coherence cliff at 64 B did not appear, the Phase 2 inflection occurred at p = 7 → 8 rather than at p > 14, and tiling did not beat the naive kernel. In all three cases the cause is that **the interpreter and the system's overheads dominate the effect being measured**. Compiled code would show the textbook result.
- **A common thread:** about 4× parallel efficiency loss shows up in strong scaling (S ≈ 3.8), weak scaling (3.67), and the roofline compute test (11.7 MFLOP/s per worker). Check power mode, per-core load, and affinity before trusting any absolute numbers.
- **Key formulas to be able to derive:** Amdahl S = 1/(s + (1−s)/p); Gustafson S = p − α(p−1); Karp-Flatt e = (1/S − 1/p)/(1 − 1/p), where a *rising* e signals growing overhead and a *constant* e signals a fixed serial fraction; ridge point I* = P/BW; tile working set 3·BS²·8 bytes.
- **Scheduling rule of thumb:** use block static only for uniform work, cyclic for smooth skew, and dynamic with a moderate chunk size for unpredictable skew. Choose C so the number of chunks is at least several times p.
